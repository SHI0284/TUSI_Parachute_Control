## 1. 목적 및 적용 범위

본 문서는 로켓 비행 데이터를 수신·표시·기록하고 ARM/DISARM 요청을 전달하는 지상 시스템의 소프트웨어 요구사항을 정의한다. ELRS 조종기를 통한 수동 입력 전달과 하드웨어 없이 수행하는 모의시험을 포함한다.

탑재 소프트웨어의 센서 처리, 비행 상태 판단, 낙하산 제어 및 RTOS 구현은 본 문서의 직접 구현 범위에 포함하지 않는다. 해당 소프트웨어에 필요한 데이터 및 명령 인터페이스 요구사항은 포함한다.

최종 개발 대상은 실제 PCB에 업로드하여 운용하는 지상 브리지 및 조종기 펌웨어와 Ubuntu PC 지상국이다. 현재 하드웨어를 즉시 사용할 수 없어 모의 입력으로 선행 개발하지만, 실제 PCB 업로드·단품시험·무선 연동·전체 통합시험을 필수 개발 범위에 포함한다. 모의시험은 중간 검증 단계이며 최종 완료를 대체하지 않는다. 본 문서의 존재는 구현 완료 또는 비행 사용 승인을 의미하지 않는다.

## 2. 역할 및 책임

| 역할 | 책임 |
| --- | --- |
| 지상 시스템 개발 담당 | Ubuntu PC 지상국, 지상국 ESP32–E22 브리지, ELRS 조종기, 모의 로켓 및 시험 도구 개발 |
| 탑재 소프트웨어 개발 담당 | 센서 처리, 비행 상태머신, 고도·최고고도 판단, 낙하산 제어, RTOS, 로켓 측 E22 및 RP1 수신·통합 |
| 인터페이스 명세 작성 담당 | 지상 시스템 개발 담당이 수행하며 패킷, 단위, 상태 코드, 명령·응답, ELRS 채널 규격 초안을 작성·배포 |
| 탑재 인터페이스 검토 담당 | 탑재 소프트웨어 개발 담당이 수행하며 구현 가능 여부, 준비 조건 및 변경 필요 사항 회신 |

인터페이스 초안은 지상 시스템 개발 담당이 먼저 작성한다. 탑재 측 검토 결과는 결정 기록에 반영하며, 검토 전 항목을 상호 합의 완료로 취급하지 않는다.

## 3. 시스템 경계 및 기본 원칙

E22 경로: `PC 지상국 ↔ USB 시리얼 ↔ 지상국 ESP32·E22 ↔ 무선 ↔ 로켓 E22 ↔ 탑재 소프트웨어`.

ELRS 경로: `조이스틱·스위치 ↔ 조종기 입력 처리 → ELRS 송신 → RP1 수신 → 탑재 소프트웨어`.

- 지상국은 명령을 요청하고 탑재 소프트웨어가 허용 여부와 상태 변경을 결정한다.
- 브리지는 데이터 전달 및 자체 연결 상태 보고를 담당한다.
- 통신 연결 상태, 보고된 비행 상태, 데이터 유효성은 서로 구분한다.
- 실물 연결, 모의 연결, 기록 재생은 명확하게 구분한다.
- 임계값과 시간 설정은 근거 및 검증 상태를 기록한다. 미정 값을 비행용 확정값으로 사용하지 않는다.

## 4. PC 지상국 기능 요구사항

| ID | 요구사항 | 인수 기준 |
| --- | --- | --- |
| GS-01 | Ubuntu에서 실행되며 기본 기능은 오프라인으로 제공해야 한다. | 인터넷 없이 모의 비행 표시·기록 가능 |
| GS-02 | 시리얼 포트 선택, 연결, 해제, 재연결 기능을 제공해야 한다. | 포트 오류·연결 해제를 처리하고 재연결 가능 |
| GS-03 | PC–브리지 연결과 로켓 데이터 수신 상태를 구분해야 한다. | 브리지만 연결된 상황을 로켓 연결로 표시하지 않음 |
| GS-04 | 비행 상태, 제어 모드, 상대고도, 수직속도, GPS 위치 및 센서 상태를 표시해야 한다. | 예제 패킷과 화면 값 일치 |
| GS-05 | 데이터 유효 여부와 마지막 수신 이후 경과 시간을 표시해야 한다. | 수신 중단·무효 입력을 구분하여 표시 |
| GS-06 | 상대고도와 수직속도의 시간 그래프를 제공해야 한다. | 입력 시각과 그래프 시간축 일치 |
| GS-07 | ARM/DISARM 요청과 처리 결과를 표시해야 한다. | 대기·수락·거부·결과 불명 구분 |
| GS-08 | 수신 및 기록 작업이 화면 응답을 지속적으로 차단하지 않아야 한다. | 연속 수신·연결 오류 중 사용자 조작 가능 |
| GS-09 | 실물·모의·재생 모드를 화면에 표시해야 한다. | 현재 모드를 식별 가능 |
| GS-10 | 재생 모드에서 실제 장치로 명령을 송신하지 않아야 한다. | 송신 경로 차단 시험 통과 |
| GS-11 | 비행 상태머신의 전체 예정 경로와 실제 보고된 진행 상황을 시각화해야 한다. | 현재·방문 확인·미확인·미구현 상태를 구분 |
| GS-12 | 상태 전이 시각·이전 상태·새 상태·전이 사유를 이력으로 제공해야 한다. | 이벤트 패킷 및 재생 로그와 표시 일치 |
| GS-13 | 로켓이 제공하는 전이 조건의 충족 여부를 표시해야 한다. | 충족·미충족·알 수 없음을 구분하고 지상국이 자체 판정하지 않음 |

초기 화면에는 연결 상태, 비행 상태·모드, 주요 수치, 고도·속도 그래프, 명령 결과 및 이벤트 목록을 포함한다. 지도는 v0.1 필수 범위에서 제외하며 위도·경도를 우선 표시한다. 오래된 데이터는 보존할 수 있으나 최신 데이터와 시각적으로 구분해야 한다.

## 6. ARM/DISARM 요구사항

| ID | 요구사항 |
| --- | --- |
| CMD-01 | 명시적인 사용자 조작으로만 요청을 생성해야 한다. |
| CMD-02 | ARM 전 대상 로켓과 마지막 보고 상태를 표시하고 사용자 확인을 받아야 한다. |
| CMD-03 | 각 요청에 식별자를 부여하고 응답을 요청과 연결해야 한다. |
| CMD-04 | 전송 사실만으로 표시 중인 비행 상태를 변경하지 않아야 한다. |
| CMD-05 | 탑재 측은 수락·거부 결과, 사유 및 처리 후 상태를 반환해야 한다. |
| CMD-06 | 동일 요청 중복 수신으로 동작을 반복하지 않아야 한다. |
| CMD-07 | 응답 시간 초과를 결과 불명으로 표시하고 최신 상태 확인 경로를 제공해야 한다. |
| CMD-08 | 재연결·재시작 시 과거 명령을 자동 재전송하지 않아야 한다. |
| CMD-09 | 대상·세션·유효기간이 맞지 않는 요청은 탑재 측에서 거부해야 한다. |
| CMD-10 | 명령 인증과 재전송 방지 방식을 상세 명세에 정의해야 한다. |

다음 정책은 탑재 측 검토가 필요한 제안이다.

| 요청 | 허용 조건 | 결과 |
| --- | --- | --- |
| 상태 조회 | 통신 가능 | 현재 상태 반환 |
| ARM | SAFE이며 탑재 측 준비 조건 충족 | ARMED 전환 |
| DISARM | 발사 전 ARMED | SAFE 전환 |
| 그 외 상태의 ARM/DISARM | 거부 | 상태 유지 및 이유 응답 |

준비 조건은 탑재 소프트웨어 개발 담당이 구체화한다. v0.1 지상국에는 전개·착륙다리 직접 작동 명령을 포함하지 않는다. 응답 수신과 후속 상태 보고의 불일치 처리도 상세 명세에 정의해야 한다.

## 7. E22 통신 및 브리지 요구사항

| ID | 요구사항 |
| --- | --- |
| LINK-01 | 프레임 경계, 버전, 종류, 길이, 대상, 세션, 순번, 데이터 및 오류 검출 방식을 정의해야 한다. |
| LINK-02 | 분할되거나 연속해서 입력된 UART 패킷을 복원해야 한다. |
| LINK-03 | 손상 데이터 이후 정상 패킷 수신을 회복해야 한다. |
| LINK-04 | 패킷 및 대기열의 최대 크기를 제한해야 한다. |
| LINK-05 | 오래된 텔레메트리가 대기열에 무한 누적되지 않도록 해야 한다. |
| LINK-06 | 명령 응답이 텔레메트리로 인해 지속적으로 지연되지 않도록 해야 한다. |
| LINK-07 | 송수신·오류·누락 추정 통계를 제공해야 한다. |
| LINK-08 | 브리지는 비행 명령을 승인하거나 비행 상태를 변경하지 않아야 한다. |
| LINK-09 | 브리지 자체 메시지와 로켓 메시지를 구분해야 한다. |
| LINK-10 | 무선 설정과 패킷 크기에 근거하여 전송 주기 및 시간 초과를 결정해야 한다. |

CRC는 전송 오류 검출용이며 송신자 인증을 대체하지 않는다. 인코딩, 바이트 순서, CRC·인증 방식 및 대역폭 예산은 후속 상세 명세에서 고정한다.

## 8. ELRS 조종기 요구사항

| ID | 요구사항 | 검증 방법 |
| --- | --- | --- |
| RC-01 | 조이스틱·스위치를 지정 채널로 변환해야 한다. | 가상 입력과 기대 출력 비교 |
| RC-02 | 최소·중립·최대값을 보정하고 저장해야 한다. | 저장·복원 시험 |
| RC-03 | 데드밴드 및 입력 범위 제한을 적용해야 한다. | 경계·범위 초과 시험 |
| RC-04 | 채널 번호, 방향, 중립값 및 스위치 의미를 문서화해야 한다. | 송수신 측 동일 해석 확인 |
| RC-05 | 모드 전환 요청과 실제 적용 모드를 구분해야 한다. | 요청 거부 시나리오 |
| RC-06 | 탑재 측에서 입력 유효 여부와 최신성을 검사해야 한다. | 중단·오래된 입력 시험 |
| RC-07 | 전원 인가·재연결 시 스위치 위치에 대한 요청 처리 규칙을 정의해야 한다. | 시작·재연결 시험 |
| RC-08 | 링크 상실 동작을 비행 상태별로 정의해야 한다. | 모의 링크 상실 시험 |

조종기 입력 처리·송신 연동은 지상 시스템 개발 담당, RP1 수신 해석·제어 적용은 탑재 소프트웨어 개발 담당의 책임이다. E28 기반 송신 구성의 ExpressLRS 호환성은 확인 전이다. 채널값 범위, 채널 배정 및 링크 상실 정책은 임의로 확정하지 않는다.

## 9. 기록·재생 및 모의시험

## 12. 완료 기준 및 변경 관리

모의 텔레메트리·ARM/DISARM 연동, 오류 시험, 기록·재생 및 조종 입력 변환 검증은 소프트웨어 선행 개발 단계의 완료 기준이다. 최종 완료에는 실제 PCB 업로드와 제15절의 하드웨어·통합시험 통과가 필요하다. 패킷·채널 명세, 예제 데이터, 시험 도구를 탑재 소프트웨어 개발 담당에게 전달해야 한다. 미결정 항목으로 수행하지 못한 시험은 미완료로 명시한다.

실제 E22 무선 연결, ELRS–RP1 호환성, 보드 전원 재인가 및 실물 입력 시험은 각각 증빙을 남긴다. 탑재 소프트웨어를 사용할 수 없는 경우 수행한 모의 탑재 장치 시험은 실제 탑재 통합시험과 구분한다.

요구사항 ID는 유지하며 변경 시 버전, 변경 이유, 영향받는 구현·시험 및 검토 상태를 기록한다. 개발 작업과 시험 결과에는 관련 요구사항 ID를 표기한다. 후속 인터페이스 명세는 본 문서를 참조하고 변경된 규칙을 중복 정의하지 않도록 관리한다.

## 13. 사용자 동작 및 화면 상세 요구사항

### 13.1 연결과 시작

1. 프로그램 시작 시 실제 명령 송신은 비활성 상태여야 한다.
2. 운용자는 실물 연결 또는 모의 연결을 선택한다. 재생은 별도 진입 경로로 제공한다.
3. 실물 연결 시 포트·시리얼 설정을 선택하고 브리지 식별 정보와 버전을 확인한다.
4. 호환 가능한 로켓 패킷 수신 후 로켓 식별자·부팅 식별값·데이터 최신성을 표시한다.
5. 대상이 불명확하거나 프로토콜이 호환되지 않는 경우 제어 요청을 허용하지 않고 이유를 표시한다.
6. 연결 해제 시 대기 중인 명령을 성공으로 처리하지 않으며, 재연결 후 이전 요청을 자동 송신하지 않는다.

### 13.2 화면 구성

### 13.3 명령 처리 상태

요청의 표시 상태는 `확인 대기 → 송신 대기 → 응답 대기 → 수락/거부/결과 불명`으로 정의한다. 송신 전 로컬 검증 실패는 로켓의 거부와 구분한다. 수락 응답은 해당 요청의 결과이며, 화면의 현재 비행 상태는 최신 상태 보고를 기준으로 표시한다.

- 한 대상에 대해 ARM/DISARM 상태 변경 요청은 동시에 하나만 진행한다.
- 결과 불명 상태에서 동일 동작을 새 요청으로 자동 생성하지 않는다. 상태 조회와 운용자의 명시적 재확인을 통해 후속 요청을 처리한다.
- 요청 처리 이력에는 대상·부팅 세션·요청 ID·명령·송신 시각·응답 시각·결과·사유를 남긴다.
- 지연 도착한 응답은 원래 요청 이력에 연결하고 현재 로켓 상태를 과거 상태로 되돌리지 않는다.
- 중복·순서 역전 패킷 및 로켓 재부팅에 대한 갱신 규칙은 인터페이스 명세에 정의한다.

### 13.5 비행 상태머신 진행 화면

GUI는 아래 정상 경로 초안을 단계별 노드 또는 단계 띠로 표시한다. 이는 기존 프로젝트의 상태 정의를 시각화하기 위한 경로이며, 본 문서가 탑재 전이 로직을 추가하거나 승인하지 않는다. 최종 경로·분기는 탑재 측 상태 전이표와 버전으로 관리한다.

`INIT → SAFE → ARMED → LAUNCH → COAST → APOGEE → DEPLOY → STABILIZATION → GUIDED_DESCENT → FINAL_DESCENT → GROUND`

추가 경로는 `ARMED → SAFE`의 DISARM 및 현재 정의된 `INIT → FAULT` 초기화 실패를 포함한다. 다른 상태의 FAULT 전이는 탑재 측 규칙이 확인된 경우에만 추가한다.

### 14.2 회로도 기반 예비 핀맵

아래 GPIO는 제공된 회로도 이미지 판독값이며 실물 배선 검증 전이다. 펌웨어 작성 전 보드 리비전과 대조하고, 불일치 시 변경 기록을 남긴다. RX/TX는 ESP32 관점이다.

| 보드 | 기능 | 예비 GPIO |
| --- | --- | --- |
| 지상 브리지 | E22 TXD → ESP RX / ESP TX → E22 RXD | 16 / 17 |
| 지상 브리지 | E22 M0 / M1 / AUX / RESET | 25 / 26 / 27 / 14 |
| 조종기 | 조이스틱 1 X / Y | 32 / 33 |
| 조종기 | 조이스틱 2 X / Y | 34 / 35 |
| 조종기 | 가변저항 입력 | 36 |
| 조종기 | E28 MOSI / MISO / SCK / NSS | 23 / 19 / 18 / 5 |
| 조종기 | E28 DIO1 / BUSY / NRESET | 21 / 4 / 14 |
| 조종기 | E28 TX_EN / RX_EN | 26 / 27 |
| 조종기 | 회로도 PYRO_TX_SIG / LEG_TX_SIG 입력 | 17 / 25 |
| 조종기 | 부저 | 13 |

회로도의 스위치 이름만으로 무선 명령이나 동작 기능을 확정하지 않는다. 스위치 기능은 채널·명령 정책에서 별도로 정의한다. GPIO 레벨, 전원, 공통 접지, 커넥터 방향, RF 제어 신호 극성은 실물 시험 전 확인 항목이다.

상태 변경 명령의 초기 보드 시험은 전개·구동 출력이 분리되거나 더미 출력으로 대체된 구성을 기록하고 수행한다. 실제 구동기 동작 검증은 탑재 소프트웨어 개발 담당과 별도 시험 항목으로 연결한다.

손실률·왕복 지연·화면 지연·연속 운용 시간의 합격 수치는 시험 전에 승인된 설정표에 기록한다. 수치가 비어 있으면 해당 성능시험을 통과로 처리하지 않는다. 근거리 링크 통과는 예상 비행 운용 거리에서의 링크 성능 보장을 의미하지 않으며, 운용 거리·환경 시험 계획과 결과를 별도로 남긴다.

### 15.2 시험 결과 기록 양식

각 시험은 시험 ID, 날짜, 수행 역할, PCB 리비전, 펌웨어 리비전, PC 프로그램 버전, 무선·시리얼 설정, 배선·출력 연결 상태, 입력 절차, 예상 결과, 실제 결과, 로그 경로, 통과/실패/미수행 및 후속 조치를 포함한다. 실물시험과 모의시험 결과를 같은 성공 건수로 합산하지 않는다.

| DEC-14 | 실물 ARM/DISARM 시험의 출력 분리 구성 | HT-09 전 지상·탑재 담당 확인 및 시험 기록 |
| DEC-15 | 상태 이벤트 순번·전이 시각·사유·조건·지원 상태 목록 전달 규격 | 지상 담당 작성, 탑재 담당 제공 가능 여부 검토 |
| DEC-16 | GUI 데이터 갱신·오래된 데이터 기준 및 상태 이력 보존 범위 | 지상 담당 초안, 통신 주기와 함께 확정 |

GUI 완료 판정에는 UI-01~UI-08 시험 결과를 포함한다. 관련 탑재 데이터 미제공으로 검증할 수 없는 항목은 모의시험 결과와 실제 통합 미완료 상태를 각각 기록한다.

## 18. 후속 인터페이스 명세

[로켓–지상국 통신 인터페이스 v0.1](communication_interface_v0.1.md)은 본 요구사항을 구체화한 구현용 제안이다. MAVLink 2 메시지 스키마와 검증 벡터를 포함한다. 탑재 측 검토 및 RF 실측은 아직 완료되지 않았다. E22의 초기 운용안은 지상국 poll 주도 방식이며, ELRS 세부 채널·펌웨어 규격은 별도 확정한다. DEC-01·DEC-04·DEC-15의 제안 작성은 완료되었으나 상호 합의 완료로 처리하지 않는다.
