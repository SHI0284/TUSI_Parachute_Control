## 1. 목적 및 적용 범위

본 문서는 약 400m 발사 지면 기준 최고고도를 예상하는 자율 유도 낙하산 회수 미션의 지상 시스템 요구사항을 정의한다. 목표 낙하지점 설정, 비행·유도 관측, ARM/DISARM, AUTO/MANUAL 전환 요청, 긴급 전개 요청 및 착륙 후 회수를 포함한다. 조종 입력은 ELRS 경로로 전달하며 실제 PCB 운용 이전에 모의시험으로 검증한다. 400m는 사용자 제공 예상값이며 비행 임계값이 아니다.

탑재 소프트웨어의 센서 처리, 비행 상태 판단, 낙하산 제어 및 RTOS 구현은 본 문서의 직접 구현 범위에 포함하지 않는다. 해당 소프트웨어에 필요한 데이터 및 명령 인터페이스 요구사항은 포함한다.

최종 개발 대상은 실제 PCB에 업로드하여 운용하는 지상 브리지 및 조종기 펌웨어와 Ubuntu PC 지상국이다. 현재 하드웨어를 즉시 사용할 수 없어 모의 입력으로 선행 개발하지만, 실제 PCB 업로드·단품시험·무선 연동·전체 통합시험을 필수 개발 범위에 포함한다. 모의시험은 중간 검증 단계이며 최종 완료를 대체하지 않는다. 본 문서의 존재는 구현 완료 또는 비행 사용 승인을 의미하지 않는다.

## 3. 시스템 경계 및 기본 원칙

E22 경로: `PC 지상국 ↔ USB 시리얼 ↔ 지상국 ESP32·E22 ↔ 무선 ↔ 로켓 E22 ↔ 탑재 소프트웨어`.

ELRS 경로: `조이스틱·스위치 ↔ 조종기 입력 처리 → ELRS 송신 → RP1 수신 → 탑재 소프트웨어`.

- 지상국은 명령을 요청하고 탑재 소프트웨어가 허용 여부와 상태 변경을 결정한다.
- 브리지는 데이터 전달 및 자체 연결 상태 보고를 담당한다.
- 통신 연결 상태, 보고된 비행 상태, 데이터 유효성은 서로 구분한다.
- 실물 연결, 모의 연결, 기록 재생은 명확하게 구분한다.
- 임계값과 시간 설정은 근거 및 검증 상태를 기록한다. 미정 값을 비행용 확정값으로 사용하지 않는다.

| ID | 요구사항 |

| CMD-10 | 명령 인증과 재전송 방지 방식을 상세 명세에 정의해야 한다. |

다음 정책은 탑재 측 검토가 필요한 제안이다.

| 요청 | 허용 조건 | 결과 |
| --- | --- | --- |
| 상태 조회 | 통신 가능 | 현재 상태 반환 |
| ARM | SAFE이며 탑재 측 준비 조건 충족 | ARMED 전환 |
| DISARM | 발사 전 ARMED | SAFE 전환 |
| 그 외 상태의 ARM/DISARM | 거부 | 상태 유지 및 이유 응답 |

준비 조건은 탑재 소프트웨어 개발 담당이 구체화한다. ConOps의 긴급 낙하산 전개 요청은 최종 필수 범위에 포함한다. 통신 계층의 직접 출력 구동은 금지하며 FSM이 검증·처리한다. 긴급 요청의 허용 상태·유효기간·최대 지연·중복 방지 규칙이 확정되기 전에는 실물 송신을 활성화하지 않는다. 착륙다리 직접 작동 명령은 원문에서 명확히 요구하지 않으므로 추가하지 않는다. 응답 수신과 후속 상태 보고의 불일치 처리도 상세 명세에 정의해야 한다.

## 12. 완료 기준 및 변경 관리

목표 설정·모드 전환·긴급 요청을 포함한 모의 미션 명령, 텔레메트리, 오류 시험, 기록·재생 및 조종 입력 변환 검증은 소프트웨어 선행 개발 단계의 완료 기준이다. 최종 완료에는 실제 PCB 업로드와 제15절의 하드웨어·통합시험 통과가 필요하다. 패킷·채널 명세, 예제 데이터, 시험 도구를 탑재 소프트웨어 개발 담당에게 전달해야 한다. 미결정 항목으로 수행하지 못한 시험은 미완료로 명시한다.

실제 E22 무선 연결, ELRS–RP1 호환성, 보드 전원 재인가 및 실물 입력 시험은 각각 증빙을 남긴다. 탑재 소프트웨어를 사용할 수 없는 경우 수행한 모의 탑재 장치 시험은 실제 탑재 통합시험과 구분한다.

요구사항 ID는 유지하며 변경 시 버전, 변경 이유, 영향받는 구현·시험 및 검토 상태를 기록한다. 개발 작업과 시험 결과에는 관련 요구사항 ID를 표기한다. 후속 인터페이스 명세는 본 문서를 참조하고 변경된 규칙을 중복 정의하지 않도록 관리한다.

## 13. 사용자 동작 및 화면 상세 요구사항

### 13.1 연결과 시작

1. 프로그램 시작 시 실제 명령 송신은 비활성 상태여야 한다.
2. 운용자는 실물 연결 또는 모의 연결을 선택한다. 재생은 별도 진입 경로로 제공한다.
3. 실물 연결 시 포트·시리얼 설정을 선택하고 브리지 식별 정보와 버전을 확인한다.
4. 호환 가능한 로켓 패킷 수신 후 로켓 식별자·부팅 식별값·데이터 최신성을 표시한다.
5. 대상이 불명확하거나 프로토콜이 호환되지 않는 경우 제어 요청을 허용하지 않고 이유를 표시한다.
6. 연결 해제 시 대기 중인 명령을 성공으로 처리하지 않으며, 재연결 후 이전 요청을 자동 송신하지 않는다.

### 13.3 명령 처리 상태

일반 요청의 표시 상태는 `확인 대기 → 송신 대기 → 응답 대기 → 수락/거부/결과 불명`으로 정의한다. 긴급 요청에 동일한 왕복 확인 횟수를 자동 적용하지 않으며, 별도로 확정한 운용 확인·허용 지연 정책을 따른다. 송신 전 로컬 검증 실패는 로켓의 거부와 구분한다. 수락 응답은 해당 요청의 결과이며, 화면의 현재 비행 상태는 최신 상태 보고를 기준으로 표시한다.

- 한 대상에 대한 일반 상태 변경 요청은 동시에 하나만 진행한다. 긴급 전개 요청은 일반 요청 대기에 묶이지 않도록 별도 우선 경로를 설계하며, 선점·원자성·결과 처리 규칙 확정 전에는 실물 활성화하지 않는다.
- 결과 불명 상태에서 동일 동작을 새 요청으로 자동 생성하지 않는다. 상태 조회와 운용자의 명시적 재확인을 통해 후속 요청을 처리한다.
- 요청 처리 이력에는 대상·부팅 세션·요청 ID·명령·송신 시각·응답 시각·결과·사유를 남긴다.
- 지연 도착한 응답은 원래 요청 이력에 연결하고 현재 로켓 상태를 과거 상태로 되돌리지 않는다.
- 중복·순서 역전 패킷 및 로켓 재부팅에 대한 갱신 규칙은 인터페이스 명세에 정의한다.

| 기록·경보 | 기록 경로·상태, 저장 실패, 오류 및 이벤트 | 시각·출처·심각도와 함께 표시 |

색상 외에 상태명·아이콘·문구를 함께 사용한다. 단위 없는 수치, 무효값의 0 대체, 마지막 정상값을 최신값처럼 표시하는 동작은 허용하지 않는다.

### 13.5 비행 상태머신 진행 화면

GUI는 아래 정상 경로 초안을 단계별 노드 또는 단계 띠로 표시한다. 이는 기존 프로젝트의 상태 정의를 시각화하기 위한 경로이며, 본 문서가 탑재 전이 로직을 추가하거나 승인하지 않는다. 최종 경로·분기는 탑재 측 상태 전이표와 버전으로 관리한다.

`INIT → SAFE → ARMED → LAUNCH → COAST → APOGEE → DEPLOY → STABILIZATION → GUIDED_DESCENT → FINAL_DESCENT → GROUND`

추가 경로는 `ARMED → SAFE`의 DISARM 및 현재 정의된 `INIT → FAULT` 초기화 실패를 포함한다. 다른 상태의 FAULT 전이는 탑재 측 규칙이 확인된 경우에만 추가한다.

| 상태 | 화면 설명 | 표시 시 주의 사항 |
| --- | --- | --- |
| INIT | 초기화 중 | 지원되는 초기화·센서 점검 결과 표시 |
| SAFE | 비행 준비 대기 | ARM 준비 조건·거부 사유 표시 |
| ARMED | 발사 감지 대기 | ARM 요청 시각과 실제 진입 시각 구분 |
| LAUNCH | 발사 감지 후 비행 단계 | 탑재 보고된 발사 시각 기준 |
| COAST | 관성 상승 단계 | 고도·수직속도와 함께 표시 |
| APOGEE | 최고고도 판정 단계 | 예측값과 실제 상태 전이를 구분 |
| DEPLOY | 낙하산 전개 처리 단계 | 상태 진입을 물리적 전개 성공으로 단정하지 않음 |

### 14.2 회로도 기반 예비 핀맵

아래 GPIO는 제공된 회로도 이미지 판독값이며 실물 배선 검증 전이다. 펌웨어 작성 전 보드 리비전과 대조하고, 불일치 시 변경 기록을 남긴다. RX/TX는 ESP32 관점이다.

| 보드 | 기능 | 예비 GPIO |
| --- | --- | --- |
| 지상 브리지 | E22 TXD → ESP RX / ESP TX → E22 RXD | 16 / 17 |
| 지상 브리지 | E22 M0 / M1 / AUX / RESET | 25 / 26 / 27 / 14 |
| 조종기 | 조이스틱 1 X / Y | 32 / 33 |
| 조종기 | 조이스틱 2 X / Y | 34 / 35 |
| 조종기 | 가변저항 입력 | 36 |
| 조종기 | E28 MOSI / MISO / SCK / NSS | 23 / 19 / 18 / 5 |
| 조종기 | E28 DIO1 / BUSY / NRESET | 21 / 4 / 14 |
| 조종기 | E28 TX_EN / RX_EN | 26 / 27 |
| 조종기 | 회로도 PYRO_TX_SIG / LEG_TX_SIG 입력 | 17 / 25 |
| 조종기 | 부저 | 13 |

회로도의 스위치 이름만으로 무선 명령이나 동작 기능을 확정하지 않는다. 스위치 기능은 채널·명령 정책에서 별도로 정의한다. GPIO 레벨, 전원, 공통 접지, 커넥터 방향, RF 제어 신호 극성은 실물 시험 전 확인 항목이다.

상태 변경 명령의 초기 보드 시험은 전개·구동 출력이 분리되거나 더미 출력으로 대체된 구성을 기록하고 수행한다. 실제 구동기 동작 검증은 탑재 소프트웨어 개발 담당과 별도 시험 항목으로 연결한다.

손실률·왕복 지연·화면 지연·연속 운용 시간의 합격 수치는 시험 전에 승인된 설정표에 기록한다. 수치가 비어 있으면 해당 성능시험을 통과로 처리하지 않는다. 근거리 링크 통과는 예상 비행 운용 거리에서의 링크 성능 보장을 의미하지 않으며, 운용 거리·환경 시험 계획과 결과를 별도로 남긴다.

### 15.2 시험 결과 기록 양식

각 시험은 시험 ID, 날짜, 수행 역할, PCB 리비전, 펌웨어 리비전, PC 프로그램 버전, 무선·시리얼 설정, 배선·출력 연결 상태, 입력 절차, 예상 결과, 실제 결과, 로그 경로, 통과/실패/미수행 및 후속 조치를 포함한다. 실물시험과 모의시험 결과를 같은 성공 건수로 합산하지 않는다.

## 20. NURA 검토 후 확정한 PC 구현 기준

이 절은 지상 담당의 구현 기준이다. 탑재 담당의 비행 정책 승인이나 실물 무선 성능 확정을 의미하지 않는다. 초기 구현은 Python Flask·pyserial 백엔드와 HTML/CSS/일반 JavaScript 프런트엔드로 구성한다. Chart.js와 Leaflet 자산은 로컬에 저장하며 의존성 버전은 구현 시 잠금 파일로 고정한다. PyQt와 별도 Node 서버는 초기 범위에 포함하지 않는다.

### 20.1 실행 및 데이터 흐름

```text
실물 USB / 모의 프레임 / 기록 재생
                 ↓ 입력 어댑터 (실행당 한 모드)
검증·디코딩 → 세션별 상태 저장소 → HTTP 조회 → 브라우저
      ↓              ↑
원본·이벤트 기록      명령 결과 반영
                     ↑
브라우저 요청 → 명령 서비스 → 단일 시리얼 소유자 → E22 브리지
```

| ID | 확정 요구사항 | 확인 방법 |
| --- | --- | --- |
| WEB-01 | 서버는 기본 `127.0.0.1`에서 단일 프로세스로 실행한다. 하나의 전송 서비스만 시리얼 포트를 소유하며 웹 요청 핸들러는 포트를 직접 읽지 않는다. | 동시 두 브라우저 접속 시 시리얼 reader 한 개 |
| WEB-02 | 수신·기록·모의 시계는 화면 조회와 독립적으로 진행한다. GET 요청은 입력을 소비하거나 모의 비행을 전진시키지 않는다. | 탭 닫기·화면 일시정지 중 수신과 기록 지속 |
| WEB-03 | 초기 화면 조회 목표는 250ms 간격이며 이전 요청 완료 뒤 다음 요청을 예약한다. 이는 RF 송신 주기가 아니다. 그래프는 동일 snapshot을 중복 추가하지 않는다. | 느린 HTTP 응답에서 요청 누적·중복 점 없음 |
| WEB-04 | 입력 모드 REAL/SIM/REPLAY를 상시 표시한다. REPLAY는 명령 서비스를 차단하고 SIM은 모의 장치로만 송신한다. 모드 변경은 명시적 세션 재시작으로 수행한다. | 모드별 송신 대상 및 차단 시험 |
| WEB-05 | 그래프 초기화·재생 위치 이동·브라우저 재접속은 탑재 reset이나 ARM을 발생시키지 않는다. | 해당 조작 중 송신 기록 비교 |
| WEB-06 | 명령 대기는 비동기로 처리하고 수신·화면 갱신을 막지 않는다. 서버 큐 포화와 로그 오류는 화면에서 확인 가능해야 한다. | 응답 유실 중 텔레메트리 지속 |
| WEB-07 | 정상 앱 실행과 펌웨어 빌드·업로드를 분리한다. 연결만으로 PCB에 자동 업로드하지 않는다. | 시작 경로 검사 |

### 20.2 화면 구성

| 영역 | 표시 및 기능 |
| --- | --- |
| 공통 상단 | REAL/SIM/REPLAY, 기체·부팅 세션, E22/ELRS 각각의 상태, 데이터 나이, 실제 FSM·실제 제어 모드, 기록 상태 |
| 미션 화면 왼쪽 | 발사 위치·현재 위치·적용 목표·궤적, 거리·방위·course error. 타일 없이도 동작하는 로컬 평면 표시를 필수로 제공 |
| 미션 화면 중앙 | 발사 지면 상대고도·수직속도 그래프, 고도 기준 표시, GNSS 품질·배터리·센서 유효성, 전이 마커 |
| 미션 화면 오른쪽 | 목표 편집값/적용값/readback, 동체 ARM 버튼·armed readback, AUTO/MANUAL 요청, 단계별 요청 가능 여부·거부 사유 |
| 미션 화면 하단 | 현재 FSM, 확인된 방문 이력·전이 시각·사유, 최근 명령 결과. 중간 미수신 상태는 미확인으로 유지 |
| 진단 탭 | 프레임 수·손상·중복·누락·역순·서명 거부·큐 상태·브리지 정보·원시 상태 코드 |
| 기록/재생 탭 | 세션 선택·시간 이동·배속·이벤트 탐색·CSV 내보내기. 실물 송신 불가 표시 |
| 설정 탭 | 포트·미션/발사 위치·단위 표시·로그 경로·설정 버전. 연결 중 전송 설정 변경은 세션 재시작 필요 |

긴급 요청은 일반 ARM 조작과 구분되는 별도 확인 화면을 갖는다. TBC-EMG-01 해소 전 실제 송신은 비활성으로 두고 이유를 표시한다. NURA의 고정 발사 위치, 시간 기반 상태 추정, 강제 전개 후 화면 상태 덮어쓰기는 이식하지 않는다. AGL 미제공 시 상대고도를 AGL로 대체하지 않는다.

### 20.3 기록 및 재생

현재 세션 원본은 SIM/REAL로 분리한 SQLite DB의 session/records 테이블이다. 이전 manifest.json/events.jsonl 구성 제안은 대체한다. 아래 항목 중 명령 수명주기·인증·독립 전이 이벤트는 해당 인터페이스 구현 후 추가할 요구이며 현재 기록은 raw_frame/packet/rejection이다. manifest에는 소스 모드, 앱/스키마/설정 버전, 기체 및 부팅 세션, 시작 UTC를 기록한다. 이벤트에는 PC UTC·단조 시각, 원본 프레임, 검증 결과, 디코딩 값, 상태 전이, 명령 수명주기 및 유실 진단을 기록한다. 인증 키는 저장하지 않는다. CSV는 분석용 내보내기이며 원본을 대체하지 않는다.

기록 작업은 별도 큐로 수행한다. 큐 상한·디스크 오류·누락 건수를 보고하고, 기록 실패를 정상 기록 중으로 표시하지 않는다. flush는 전원 상실 내구성 보장이 아니므로 종료 flush 및 복구 시험을 별도로 수행한다. 버퍼 크기와 저장 주기는 부하 시험 후 설정값으로 고정한다.

추가 인수시험: 두 브라우저에서 같은 snapshot 조회, 브라우저 종료 중 기록, 느린 조회 중 중복 방지, 미지 FSM 코드, 인터넷 없는 위치 표시, 세션 변경 중 과거 명령 차단, 로그 일부 손상 후 재생 가능한 범위 식별을 검사한다. 관련 API 계약은 ICD v0.2 §18을 따른다.

## 2026-11-19 구현 계약 추가

- 중앙 3D는 제공된 OpenRocket 외형 치수로 구성한다. 도색·캐노피 형상은 개념 시각화임을 명시한다.
- recovery.main/drogue 보고가 없으면 FSM DEPLOY만으로 물리적 전개를 표시하지 않는다. physical_confirmed는 전개율·상태와 별도 표시한다.
- arming.source=AIRFRAME_BUTTON, button_pressed 및 armed는 bool/null인 선택 보고 필드다. 최종 binary wire allocation은 별도 확정한다.
- SQLite 세션 기록과 60초/정상종료 백업을 구현한다. 큐·디스크 실패·누락은 UI에서 식별할 수 있어야 한다. 백업은 최근 3개 보관하고 원본은 자동 삭제하지 않는다.
- 비행 기록 재생 UI, 최종 RF binary decoder, 실제 탑재 버튼/센서/낙하산 확인 신호 시험은 미완료다.
